00开始之前

所有教程都把这三个东西混着讲，先把它们拆开。

Git · 工具

装在你电脑上的版本管理软件。它记录"哪个文件、什么时候、被谁、改成了什么样"。离线也能用，不需要网络。

GitHub · 网站

一个云端仓库托管平台。它存放 Git 仓库，顺带提供协作、开源、Pages 建站、Actions 自动化。它不是 Git 本身。

客户端 · 操作方式

你指挥 Git 的手。可以是终端敲命令，也可以是 GitHub Desktop / VS Code 的图形界面。本质做的是同一件事。

一句话记住：Git 是本地记账本，GitHub 是云端保险柜。你在本地记账，然后同步到云端。

01安装与配置

十分钟搞定，配好之后就不用再管了。

装 Git

去 git-scm.com 下载 Windows 版，一路点"下一步"用默认设置就行。

装完打开终端（PowerShell 或 Git Bash），输入下面这行验证：

terminal
git --version
# 输出类似 git version 2.47.0 就成功了

配置身份

告诉 Git 你是谁。这一步只做一次，全局生效，之后每次提交都会自动带上这个信息。

terminal
git config --global user.name "你的名字"
git config --global user.email "你的邮箱@example.com"

注意：这里的邮箱最好和你 GitHub 账号的邮箱一致，否则提交记录里不会显示你的头像，也不会算进你的贡献格子。

注册 GitHub 账号

去 github.com 注册。用户名要慎重选——它会出现在你的主页地址和 Pages 网址里（用户名.github.io），而且以后改起来会影响已有链接。

配置认证（关键，很多人卡在这）

GitHub 早就不允许用账号密码推送了，必须用 Personal Access Token 或 SSH 密钥。新手推荐前者：

GitHub 网页 → 右上角头像 → Settings → 左侧最下面 Developer settings → Personal access tokens → Tokens (classic) → Generate new token，勾选 repo 权限，生成后立刻复制保存（关掉页面就再也看不到了）。

之后 git push 提示输密码时，粘贴这个 token 即可。

更省事的办法：装一个 GitHub Desktop 或在 VS Code 里登录 GitHub 账号，它会自动帮你处理认证，不用手搓 token。

02四个区域

看懂这张图，你就理解了 90% 的 Git 操作。所谓"用 GitHub"，本质就是在四个格子之间搬东西。

工作区→ git add→ 暂存区→ git commit→ 本地仓库→ git push→ GitHub 远程仓库
区域是什么怎么进去
工作区你电脑上正在编辑的文件，改了什么它都看得见直接编辑文件
暂存区一份"这次要提交什么"的清单，还没进历史git add
本地仓库完整的版本历史，存在你电脑的 .git 文件夹里git commit
远程仓库GitHub 上的那份，多人协作和备份的集散地git push

为什么要有个"暂存区"？

这是新手最困惑的地方。你可能会想：改完直接提交不就行了？

假设你今天改了三个文件：修了一个 bug、加了一个新功能、顺手调了下格式。git add 让你可以只挑出修 bug 的那两个文件提交，格式调整留到下次。这样每次提交都是一个干净、独立、说得清的小改动。三个月后回头翻历史，你会感谢当初的自己。

如果不想挑，直接 git add . 全部丢进去也没问题——先跑通流程比什么都重要。

记不住怎么办：任何时候忘了自己在哪个状态，敲 git status。它会告诉你哪些文件改了、哪些已经暂存、下一步该干什么。这是 Git 里最有用的一条命令。

03命令速查

这些覆盖了 95% 的日常场景。不用背，需要时回来查。

查看状态

命令作用
git status看当前状态：哪些改了、哪些已暂存
git log --oneline看提交历史，一行一条，最清爽
git diff看具体改了哪几行（还没 add 的）
git diff --staged看已经 add 的改动内容
git branch列出所有分支，当前分支前面有 *

提交改动

命令作用
git add .所有改动加入暂存区
git add 文件名只加某个文件
git commit -m "说明"存成一个版本快照
git commit -am "说明"跳过 add，直接提交已跟踪文件的改动

同步远程

命令作用
git clone 地址把别人的仓库整份拷到本地
git pull把远程的更新拉下来并合并
git push把本地的提交推上去
git remote -v查看关联的远程仓库地址

撤销与回退

命令作用危险度
git restore 文件名丢弃某个文件未暂存的改动中
git restore --staged 文件名把文件从暂存区拿出来，改动还在低
git commit --amend修改最后一次提交（比如写错说明）中
git reset --soft HEAD~1撤销最后一次提交，改动保留在暂存区中
git reset --hard HEAD~1撤销提交并丢弃改动高
git reflog救命的后悔药，能找回几乎所有操作安全

关于 --hard：它会真的删掉你的改动，且不在回收站里。用之前先 git status 确认一下，或者先 git stash 存起来。真删错了也别慌，git reflog 通常能救回来。

04实操：把项目推上 GitHub

从零开始，把一个本地文件夹变成 GitHub 上的仓库。跟着敲一遍就懂了。

在 GitHub 上先建一个空仓库

网页右上角 + → New repository。填仓库名（建议英文小写加连字符，比如 my-blog）。

关键：不要勾选 "Add a README file"、不要加 .gitignore、不要选 License。就建一个完全空的仓库。

为什么？如果远程仓库不是空的（已经有 README），而你的本地也是新建的，两边都有内容但互不相识，push 时会报错。新手最容易死在这一步。空仓库最省事。

建好后页面会显示一段命令，复制那个仓库地址备用。

把本地文件夹变成 Git 仓库

打开终端，cd 到你的项目文件夹，然后：

terminal
cd /h/我的项目            # 进入项目目录
git init                  # 把这个文件夹变成 Git 仓库
git branch -M main        # 主分支命名为 main（GitHub 的默认叫法）

执行 git init 后，文件夹里会多出一个隐藏的 .git 目录，那就是本地仓库本体。

第一次提交

terminal
git add .                        # 所有文件加入暂存区
git commit -m "初始化项目"        # 存成第一个版本快照
git status                       # 确认一下：应该显示 working tree clean

关联远程仓库

terminal
git remote add origin https://github.com/你的用户名/仓库名.git
git remote -v                    # 确认关联成功

origin 只是给这个远程地址起的外号，你也可以叫别的，但约定俗成都用 origin。

推送上去

terminal
git push -u origin main

-u 的意思是"记住这个关联关系"。第一次推送加它，以后直接敲 git push 就够了。

提示输密码时，粘贴你之前生成的 Personal Access Token。

刷新 GitHub 页面，文件应该都在了。

完整命令汇总（可以存下来）：

第一次推送的完整流程
cd /h/我的项目
git init
git branch -M main
git add .
git commit -m "初始化项目"
git remote add origin https://github.com/你的用户名/仓库名.git
git push -u origin main

05实操：拉别人的仓库

这个更简单，一条命令。

terminal
cd /h/存放位置
git clone https://github.com/用户名/仓库名.git

# 想指定文件夹名
git clone https://github.com/用户名/仓库名.git 我的文件夹名

克隆下来的仓库已经自动配好了 origin，可以直接 git pull / git push。

几种常见情况

情况怎么做
只想看看源码，不改直接 clone，或者网页上点 "Download ZIP"
想参与贡献先 Fork（网页右上角按钮）到你账号下，再 clone 自己的 fork
克隆太慢加 --depth 1 只拉最新一次提交，体积小很多
想换成 SSH 方式git remote set-url origin git@github.com:...

Fork 和 Clone 的区别：Clone 是把仓库拷到你电脑上，Fork 是把它拷到你 GitHub 账号下。想给别人贡献代码，通常要先 Fork 再 Clone。

06分支：为什么需要它

分支就是"平行世界"。你可以在里面随便折腾，搞砸了也不影响主线。

主分支（main）上的代码应该永远是能用的。但你要开发新功能、做实验、试一个不知道行不行的想法——这时候就开一个分支。

main→ git switch -c 新功能→ 在分支上改改改→ 合并回 main
命令作用
git branch列出所有分支
git switch -c 分支名创建并切换到新分支
git switch 分支名切换到已有分支
git merge 分支名把指定分支合并到当前分支
git branch -d 分支名删除分支（已合并的）
git branch -D 分支名强制删除（未合并也删）

一个完整的流程

bash
git switch -c add-navbar      # 开个分支做导航栏
# ... 改代码 ...
git add .
git commit -m "添加顶部导航栏"
git switch main               # 回到主分支
git merge add-navbar          # 把导航栏合并进来
git push                      # 推到 GitHub
git branch -d add-navbar      # 分支没用了，删掉

老教程用的是 git checkout，新版本推荐 git switch。功能一样，但 switch 专门管切换分支，语义更清晰，不容易误操作。两个都能用。

冲突是什么

如果你在分支上改了某一行，主分支上也改了同一行，合并时 Git 就不知道听谁的，会停下来问你。这叫合并冲突。

文件里会出现这样的标记：

冲突标记
<<<<<<< HEAD
这是主分支上的内容
=======
这是分支上的内容
>>>>>>> add-navbar

处理办法：手动编辑文件，删掉这些标记，保留你想要的内容（或者两者都要），然后 git add + git commit 完成合并。

冲突不可怕，它只是 Git 在说"这里需要人做决定"。

07.gitignore：别把垃圾传上去

建仓库第一件事就该做这个。不然你的仓库会瞬间膨胀到几百 MB。

在项目根目录建一个文件叫 .gitignore（注意前面有个点，没有扩展名），里面写上不想被 Git 跟踪的文件或文件夹，一行一个。

.gitignore
# 依赖包，体积巨大，别人 clone 后自己装就行
node_modules/
venv/
__pycache__/

# 构建产物，可以重新生成
dist/
build/
*.pyc

# 系统文件
.DS_Store
Thumbs.db
desktop.ini

# 编辑器和 IDE 配置
.vscode/
.idea/
*.swp

# 日志和缓存
*.log
.cache/

# 密钥和隐私文件 —— 最重要的一项
.env
.env.local
*.key
*.pem
secrets.json

# 临时文件
*.tmp
*.bak

最重要的一条：密钥永远不要提交。API key、数据库密码、token，一旦推到公开仓库就等于公开了。GitHub 上有机器人 24 小时扫描，几分钟内就会有人来试你的密钥。

如果已经推上去了：立刻去对应平台作废那个密钥重新生成，然后从代码里删掉。单纯删文件重新提交是不够的——历史记录里还在。

已经被跟踪的文件怎么排除

如果文件之前已经提交过，光加进 .gitignore 是没用的（Git 会继续跟踪它）。需要先把它从跟踪列表里移除：

terminal
git rm -r --cached 文件夹名      # 从跟踪中移除，但保留本地文件
git commit -m "移除不该跟踪的文件"

偷懒办法：建仓库时在 GitHub 页面勾选 .gitignore 模板，选你的语言，它会自动生成一份标准配置。省得自己写。

08排错手册

新手会遇到的报错，九成在这张表里。

报错关键词原因解决
rejected ... fetch first 远程有你本地没有的提交（通常是网页上改了东西） 先 git pull 再 git push
failed to push ... non-fast-forward 同上，本地落后于远程 git pull --rebase 然后 git push
Authentication failed 密码方式已被禁用 改用 Personal Access Token 或 SSH 密钥
Updates were rejected 远程仓库不是空的，本地有独立历史 要么先 git pull --allow-unrelated-histories，要么新建一个空仓库
CONFLICT (content) 合并冲突，两边改了同一处 手动编辑文件解决冲突后 git add + git commit
fatal: not a git repository 当前目录不是 Git 仓库 cd 到正确目录，或 git init
Please tell me who you are 没配 user.name / user.email 回到第 1 节配置身份
nothing to commit 没有新改动，或者忘了 git add 正常提示。检查是否已 add
file too large 单文件超过 100MB 用 Git LFS，或者别把大文件放进仓库

万能三步：遇到任何问题，先做这三件事——git status 看状态 → 完整读一遍报错信息 → 把报错原文粘到搜索引擎。Git 的报错信息其实写得很清楚，只是新手习惯性跳过不读。

救命命令：git reflog

如果你不小心 reset --hard 删了东西，或者搞乱了分支，git reflog 会列出你所有的操作记录（包括已经"丢失"的提交）。找到你想回去的那个哈希值，然后：

terminal
git reflog
# 输出类似：a1b2c3d HEAD@{3}: commit: 添加导航栏
git reset --hard a1b2c3d

只要提交过，基本都能找回来。Git 比你想的宽容得多。

09GitHub Pages：免费托管网站

对你最实用的一节。GitHub 把仓库里的静态文件变成网站，白送。

它能做什么，不能做什么

能做

个人博客、项目文档、作品集、落地页、纯前端小工具。只托管 HTML / CSS / JS / 图片这类静态文件。

不能做

不能跑后端（PHP / Python / Node）、没有数据库、没有服务端渲染。需要登录和数据的动态站做不了。

免费额度（官方口径）

项目限制说明
站点大小1 GB源仓库也建议 ≤ 1GB
月带宽100 GB软限制，个人博客远远用不到
构建频率10 次 / 小时软限制，用自定义 Actions 工作流可绕过
部署超时10 分钟超时算失败
费用公开仓库 $0私有仓库需要 Pro（$4/月）

"软限制"的意思是超了不会立刻封，GitHub 会发邮件提醒你优化或换地方。对个人站来说，每天几千访问量都碰不到上限。

部署流程

准备文件

仓库根目录必须有 index.html（这是默认首页）。CSS、JS、图片一起推上去。

开启 Pages

仓库页面 → Settings → 左侧栏 Pages → Source 选 Deploy from a branch → 分支选 main，文件夹选 / (root) → Save。

等一分钟

GitHub 会自动构建部署。回到 Pages 设置页，顶部会出现你的网址：

你的网址
https://你的用户名.github.io/仓库名/

如果仓库名就叫 你的用户名.github.io，那网址就是 https://你的用户名.github.io/，不带后缀，看起来更正式。

以后更新

每次 git push，Pages 会自动重新部署，大约一分钟生效。不用做任何额外操作。

绑定自己的域名

想让网址变成 www.你的域名.com：

  1. 在域名服务商那边加一条 CNAME 记录，指向 你的用户名.github.io
  2. 在 Pages 设置页的 Custom domain 填上你的域名，保存
  3. 等 DNS 生效（几分钟到几小时），勾选 Enforce HTTPS

HTTPS 证书 GitHub 会自动签发，不用自己搞。

两个容易踩的坑：

1. 用静态生成器要加 .nojekyll——Hexo、Hugo、Astro 这类工具生成的 _ 开头的目录会被 Jekyll 吃掉。在仓库根目录建一个空的 .nojekyll 文件即可。

2. 免费账号只能从公开仓库发 Pages——想源码不公开又要 Pages，得升 Pro。

使用条款的边界

官方明确禁止把 Pages 当在线商店、电商站、或者以商业交易/SaaS 为主的网站的免费主机。个人博客、文档站、作品展示完全没问题。如果哪天要接支付卖东西，就得换 Cloudflare Pages 或者买服务器了。

现在就可以试：你手上这份文档就是最好的练手素材。把它推到一个公开仓库，开 Pages，一分钟后你就有自己的网站了。比任何教程都直观。

10Issues / PR / Actions

GitHub 不只是存代码，这三个功能是它作为协作平台的核心。

Issues · 任务清单

用来记待办、报 bug、提需求。可以打标签、指派给人、关联到某个提交。你自己的项目也可以用它记想法，比记在备忘录里强。

Pull Request · 合并请求

简称 PR。你改完代码，发起一个 PR 说"我想把这些改动合并进主分支"。别人可以在上面逐行评论、提意见，讨论清楚了再合并。

Actions · 自动化

GitHub 提供的免费服务器。你写一段配置，它就能在你 push 代码后自动跑测试、自动构建、自动部署。Pages 的自动发布就是靠它。

PR 的标准流程

给别人的项目提改动
# 1. 在网页上 Fork 目标仓库到你账号下
# 2. 克隆你自己的 fork
git clone https://github.com/你的用户名/目标仓库.git

# 3. 开一个分支改代码
git switch -c fix-typo

# 4. 提交并推到你的 fork
git add .
git commit -m "修复文档中的拼写错误"
git push origin fix-typo

# 5. 回到 GitHub 网页，点 "Compare & pull request" 发起 PR

Actions 长什么样

在仓库里建 .github/workflows/ 目录，放一个 YAML 文件：

.github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build
      - uses: actions/deploy-pages@v4

意思是：每次 main 分支有推送，就在一台 Ubuntu 机器上跑一遍构建，然后把产物发布到 Pages。免费账号每月有 2000 分钟的 Actions 额度，个人项目根本用不完。

11每日工作流

学到这里，你实际每天要做的就这几步。重复一辈子。

日常循环
git pull                      # 1. 先拉，避免冲突
# 2. 改你的文件
git status                    # 3. 看看改了啥
git add .                     # 4. 加入暂存区
git commit -m "具体说明改了什么"  # 5. 存成一个版本
git push                      # 6. 推上去

顺序记住：先拉后推。这是新手踩坑最多的地方，养成习惯能避开 80% 的报错。

commit message 怎么写

三个月后的你会感谢现在的你写清楚了说明。推荐这个格式：

写法评价
update等于没写
修改了一些东西还是很模糊
修复导航栏在小屏幕上错位的问题好，一眼知道改了什么
feat: 添加文章搜索功能好，带类型前缀更规范

常见前缀：feat 新功能、fix 修 bug、docs 文档、style 格式调整、refactor 重构。

阶段目标做什么

第 1 周会用分支每个新功能开一个分支，做完合并回去
